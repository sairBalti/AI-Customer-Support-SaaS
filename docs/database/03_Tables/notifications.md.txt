# 1. Purpose

The **notifications** table stores every notification generated by the system.

Notifications inform users about important events such as:

- New support tickets
- Ticket replies
- AI escalations
- Document processing
- AI indexing completion
- User invitations
- Password resets
- Role changes
- Subscription events
- Billing events
- System alerts

The table stores notification metadata only.

Delivery is handled asynchronously by the Notification Service.

---

# 2. Business Responsibilities

The notifications table is responsible for

- Notification storage
- Delivery tracking
- Read tracking
- Notification history
- Retry management
- Multi-channel delivery
- User inbox
- Audit support

---

# 3. Business Rules

### Rule 1

Every notification belongs to one company.

---

### Rule 2

Every notification belongs to one recipient.

---

### Rule 3

A notification may reference any business entity.

Examples

- Ticket
- Chat Session
- Document
- User
- Invoice

---

### Rule 4

Notifications are immutable after creation.

Only delivery metadata may change.

---

### Rule 5

Notifications are never physically deleted.

Old notifications are archived according to the retention policy.

---

### Rule 6

Notifications are delivered asynchronously.

---

### Rule 7

Delivery failures are retried automatically.

---

### Rule 8

Every notification has exactly one type.

# 15. SQLAlchemy Model Example

```python
class Notification(Base):

    __tablename__ = "notifications"

    notification_id = mapped_column(
        BigInteger,
        primary_key=True
    )

    company_id = mapped_column(
        ForeignKey("companies.company_id"),
        nullable=False
    )

    recipient_id = mapped_column(
        ForeignKey("users.user_id"),
        nullable=False
    )

    notification_uuid = mapped_column(
        String(36),
        unique=True
    )
```

# 21. Security Considerations

- Enforce tenant isolation.
- Users may access only their own notifications.
- Validate entity ownership before generating action URLs.
- Never expose sensitive data inside notification payloads.
- Encrypt provider credentials.
- Audit notification delivery failures.

---

# 22. Performance Considerations

- Queue all outbound notifications.
- Batch email delivery where possible.
- Cache unread notification counts.
- Paginate notification history.
- Archive expired notifications.
- Use background workers for retries.

3. Support multiple delivery channels.

5. Archive expired notifications.

# 26. Architecture Notes

Recommended notification architecture

```
Business Event

↓

Domain Event

↓

Notification Service

↓

Message Queue

↓

Notification Worker

↓

Email / SMS / Push Providers

↓

Delivery Tracking

↓

User Inbox

↓

Analytics
```

The **notifications** table serves as the centralized notification history for the platform. It should remain independent of specific delivery providers through a notification gateway abstraction, enabling future support for additional communication channels without schema changes.
