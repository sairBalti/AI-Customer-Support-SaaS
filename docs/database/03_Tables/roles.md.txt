# 1. Purpose

The **roles** table defines the available user roles within the platform.

It is a core component of the **Role-Based Access Control (RBAC)** system.

Each user is assigned **exactly one role**, and each role grants a predefined set of permissions.

The `roles` table contains only role metadata. Individual permissions are managed through the `permissions` and `role_permissions` tables.

---

# 2. Business Responsibilities

The roles table is responsible for:

- Defining user roles
- Supporting RBAC
- Organizing permission groups
- Restricting feature access
- Supporting future custom roles
- Providing authorization metadata

---

# 3. Business Rules

### Rule 1

Each role must have a unique name.

---

### Rule 2

Each user must have one role.

---

### Rule 3

Roles cannot be deleted while users are assigned to them.

---

### Rule 4

System roles are protected and cannot be removed.

---

### Rule 5

Only Super Administrators may create or modify system roles.

---

### Rule 6

Role names are immutable after production deployment unless handled through a controlled migration.

---

### Rule 7

Inactive roles cannot be assigned to users.

# 5. Default System Roles

The platform includes the following predefined roles.

| Role | Description |
|-------|-------------|
| SUPER_ADMIN | Platform administrator |
| COMPANY_ADMIN | Company owner or administrator |
| SUPPORT_MANAGER | Manages support agents |
| SUPPORT_AGENT | Handles customer tickets |
| CUSTOMER | End customer using chat |

These roles are seeded during initial deployment.

- Unique

# 14. SQLAlchemy Model Example

```python
class Role(Base):
    __tablename__ = "roles"

    role_id = mapped_column(
        Integer,
        primary_key=True
    )

    role_name = mapped_column(
        String(100),
        unique=True,
        nullable=False
    )

    display_name = mapped_column(
        String(150),
        nullable=False
    )

    users = relationship(
        "User",
        back_populates="role"
    )
```

# 19. Security Considerations

- Role modification requires elevated privileges.
- System roles cannot be deleted through standard APIs.
- All role changes must be recorded in `audit_logs`.
- Authorization decisions should never rely on role names alone; use permissions where available.

---

# 20. Performance Considerations

- Cache active roles in Redis.
- Cache role-permission mappings.
- Roles change infrequently, making them ideal cache candidates.
- Refresh cache after updates.

# 22. Cursor AI Instructions

When generating code for `roles`:

1. Do not hardcode role IDs.
2. Reference roles by stable identifiers (e.g., `role_name`) in seed logic.
3. Protect system roles from deletion.
4. Keep seed data synchronized with migrations.
5. Integrate with the RBAC authorization layer.
6. Update documentation when new roles are introduced.

# 24. Recommended Future RBAC Schema

For enterprise-grade authorization, implement the following tables:

```
roles
   │
   ├──────────────┐
                  │
                  ▼
         role_permissions
                  │
                  ▼
            permissions
```

Example permissions:

```
users.create
users.read
users.update
users.delete

companies.manage

documents.upload
documents.delete

tickets.assign
tickets.close

chat.view

analytics.view

settings.manage
```

This design allows adding or removing capabilities without changing application code or creating new roles.
