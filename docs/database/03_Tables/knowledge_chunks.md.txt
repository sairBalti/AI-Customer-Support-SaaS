# 1. Purpose

The **knowledge_chunks** table stores the processed text fragments extracted from uploaded documents.

After a document is uploaded, it is parsed and divided into smaller semantic chunks. Each chunk is then converted into an embedding and stored in the configured vector database (ChromaDB, Pinecone, Qdrant, Weaviate, etc.).

This table **does not store embedding vectors**.

Instead, it stores:

- Chunk metadata
- Original text
- Chunk ordering
- Embedding references
- Retrieval metadata

The vector itself remains in the vector database.

---

# 2. Why Chunking?

Large Language Models cannot efficiently process very large documents.

Instead:

```
Upload Document

↓

Extract Text

↓

Clean Text

↓

Split Into Chunks

↓

Generate Embeddings

↓

Store Embeddings

↓

AI Search
```

Example

Original Document

```
Employee Handbook

120 Pages
```

↓

Split into

```
Chunk 1

Chunk 2

Chunk 3

...

Chunk 356
```

When a customer asks

> "How many vacation days do employees receive?"

Only the relevant chunks are retrieved.

# 4. Business Rules

### Rule 1

Every chunk belongs to exactly one company.

---

### Rule 2

Every chunk belongs to exactly one document.

---

### Rule 3

Chunk order must be preserved.

---

### Rule 4

Embeddings are stored outside MySQL.

---

### Rule 5

Deleting a document deletes all associated chunks.

---

### Rule 6

Chunks cannot exist without a parent document.

---

### Rule 7

Chunk text is immutable after indexing.

Re-indexing creates new chunks.

---

### Rule 8

Chunk size is determined by AI settings.

Example

```
800 Tokens

100 Token Overlap
```

# 14. SQLAlchemy Model Example

```python
class KnowledgeChunk(Base):
    __tablename__ = "knowledge_chunks"

    chunk_id = mapped_column(
        BigInteger,
        primary_key=True
    )

    company_id = mapped_column(
        ForeignKey("companies.company_id"),
        nullable=False
    )

    document_id = mapped_column(
        ForeignKey("documents.document_id"),
        nullable=False
    )

    chunk_text = mapped_column(
        Text,
        nullable=False
    )

    embedding_id = mapped_column(
        String(255),
        unique=True
    )

    document = relationship(
        "Document",
        back_populates="chunks"
    )
```

# 20. Security Considerations

- Every chunk belongs to one tenant.
- Never expose chunks from another company.
- Encrypt sensitive metadata where required.
- Validate document ownership before retrieval.
- Delete vectors when chunks are deleted.
- Record administrative re-index operations in audit logs.

---

# 21. Performance Considerations

- Bulk insert chunks during indexing.
- Batch embedding requests.
- Store vectors only in the vector database.
- Cache frequently retrieved metadata.
- Avoid storing duplicate chunks.
- Optimize retrieval statistics updates.

# 23. Cursor AI Instructions

When generating code for `knowledge_chunks`:

1. Never store embedding vectors in MySQL.
2. Store only embedding identifiers.
3. Generate UUIDs for every chunk.
4. Preserve chunk ordering.
5. Use bulk inserts for indexing.
6. Remove vectors when deleting chunks.
7. Keep vector database and MySQL synchronized.
8. Update retrieval statistics asynchronously.
9. Keep ORM models, migrations, repositories, services, and documentation synchronized.

# 25. Architecture Notes

## Recommended Chunk Size

| Content Type | Chunk Size | Overlap |
|--------------|-----------:|---------:|
| FAQ | 300–500 tokens | 50 |
| Product Documentation | 500–800 tokens | 100 |
| User Manuals | 700–1,000 tokens | 150 |
| Policies & Contracts | 800–1,200 tokens | 200 |

---

## Supported Vector Databases

- ChromaDB
- Pinecone
- Qdrant
- Weaviate
- Milvus
- pgvector *(Future Option)*

The implementation should abstract vector operations behind a `VectorStoreService` interface so providers can be swapped without changing application logic.
