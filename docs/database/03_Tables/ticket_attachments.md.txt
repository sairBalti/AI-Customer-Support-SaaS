# 1. Purpose

The **ticket_attachments** table stores metadata for files attached to support ticket messages.

Files themselves are **never stored inside MySQL**. Instead, they are stored in object storage such as:

- AWS S3
- Azure Blob Storage
- Google Cloud Storage
- MinIO
- Local Storage (Development)

This table stores only metadata required for retrieval, validation, auditing, and lifecycle management.

Attachments may include:

- Images
- PDFs
- Word documents
- Excel files
- ZIP archives
- Videos
- Audio recordings
- Log files
- Screenshots

# 3. Business Rules

### Rule 1

Every attachment belongs to one ticket message.

---

### Rule 2

Every attachment belongs to one company.

---

### Rule 3

Files must pass malware scanning before becoming downloadable.

---

### Rule 4

Duplicate uploads are detected using SHA-256 hashes.

---

### Rule 5

Files are immutable after upload.

---

### Rule 6

Deleting a ticket does not immediately remove physical files.

Cleanup is handled asynchronously according to the retention policy.

---

### Rule 7

Downloads require authorization.

---

### Rule 8

Attachments inherit the visibility of their parent message.

# 15. SQLAlchemy Model Example

```python
class TicketAttachment(Base):

    __tablename__ = "ticket_attachments"

    attachment_id = mapped_column(
        BigInteger,
        primary_key=True
    )

    ticket_message_id = mapped_column(
        ForeignKey("ticket_messages.ticket_message_id"),
        nullable=False
    )

    company_id = mapped_column(
        ForeignKey("companies.company_id"),
        nullable=False
    )

    uploaded_by = mapped_column(
        ForeignKey("users.user_id"),
        nullable=False
    )

    attachment_uuid = mapped_column(
        String(36),
        unique=True
    )

    message = relationship(
        "TicketMessage",
        back_populates="attachments"
    )
```

# 21. Security Considerations

- Scan every uploaded file.
- Reject infected files.
- Validate MIME type and extension.
- Encrypt files at rest.
- Generate short-lived signed download URLs.
- Enforce tenant isolation.
- Log every upload and download.
- Prevent path traversal attacks.
- Apply rate limiting to download endpoints.

---

# 22. Performance Considerations

- Store binaries outside MySQL.
- Use CDN for frequently downloaded files.
- Cache attachment metadata.
- Queue virus scanning asynchronously.
- Compress supported file types where appropriate.
- Schedule cleanup of orphaned files.

# 24. Cursor AI Instructions

When generating code for `ticket_attachments`:

3. Scan files before making them available.
4. Use signed URLs for downloads.
5. Store only metadata in the database.
6. Enforce tenant isolation.
7. Remove orphaned objects through background jobs.

# 26. Architecture Notes

Recommended attachment architecture:

```
User

↓

Upload API

↓

Validation

↓

Virus Scanner

↓

Object Storage

↓

Metadata (MySQL)

↓

Signed URL Service

↓

Authorized Download

↓

Audit Logging
```

The **ticket_attachments** table serves as the metadata layer between the support platform and the object storage service. It should remain lightweight, secure, auditable, and independent of the underlying storage provider through a storage abstraction layer.
