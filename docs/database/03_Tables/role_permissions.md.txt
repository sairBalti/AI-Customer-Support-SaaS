# 1. Purpose

The **role_permissions** table is a junction (bridge) table that implements the **many-to-many relationship** between `roles` and `permissions`.

It defines which permissions are granted to each role.

Instead of hardcoding permissions into application logic, every authorization decision should reference this table.

---

# 2. Why This Table Exists

A role can have many permissions.

A permission can belong to many roles.

Relationship

```
Roles

*

↓

Role Permissions

↑

*

Permissions
```

Without this table:

- Authorization becomes hardcoded.
- Custom roles become difficult.
- Enterprise features become limited.

---

# 3. Business Responsibilities

This table is responsible for:

- Assigning permissions to roles
- Supporting RBAC
- Permission inheritance
- Authorization mapping
- Future custom roles
- Dynamic access control

---

# 4. Business Rules

### Rule 1

Every record must reference a valid role.

---

### Rule 2

Every record must reference a valid permission.

---

### Rule 3

Duplicate mappings are not allowed.

---

### Rule 4

System mappings can only be modified by Super Administrators.

---

### Rule 5

Removing a permission immediately revokes access for every affected role.

---

### Rule 6

Permission changes should invalidate the authorization cache.

# 13. SQLAlchemy Model Example

```python
class RolePermission(Base):
    __tablename__ = "role_permissions"

    role_permission_id = mapped_column(
        BigInteger,
        primary_key=True
    )

    role_id = mapped_column(
        ForeignKey("roles.role_id"),
        nullable=False
    )

    permission_id = mapped_column(
        ForeignKey("permissions.permission_id"),
        nullable=False
    )

    granted_by = mapped_column(
        ForeignKey("users.user_id"),
        nullable=True
    )

    role = relationship(
        "Role",
        back_populates="role_permissions"
    )

    permission = relationship(
        "Permission",
        back_populates="role_permissions"
    )
```

# 19. Authorization Flow

```
User Login

↓

Load Role

↓

Load Permissions

↓

Cache Permissions

↓

Incoming API Request

↓

Permission Check

↓

Allow / Deny
```

Permissions should be loaded once and cached for the duration of the request.

---

# 20. Security Considerations

- Only authorized administrators may change role mappings.
- Every change must generate an audit log.
- Never trust permissions sent by the client.
- Refresh caches immediately after updates.
- Prevent duplicate mappings through database constraints.

---

# 21. Performance Considerations

- Cache role-permission mappings in Redis.
- Batch-load permissions to avoid N+1 queries.
- Use indexed lookups for authorization.
- Minimize database access by caching resolved permissions per request.

# 23. Cursor AI Instructions

When generating RBAC code:

1. Never hardcode permissions in controllers.
2. Always resolve permissions through `role_permissions`.
3. Enforce the unique `(role_id, permission_id)` constraint.
4. Invalidate caches after permission changes.
5. Keep ORM models, seed data, migrations, and documentation synchronized.
