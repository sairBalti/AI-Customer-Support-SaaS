# 1. Purpose

The **permissions** table defines every action that can be performed within the system.

Unlike roles, permissions represent **individual capabilities** such as:

- Create User
- Delete Document
- Assign Ticket
- View Analytics

Roles receive permissions through the **role_permissions** table.

The application **must always authorize based on permissions**, not role names.

---

# 2. Why Permissions?

Instead of checking:

```python
if user.role == "ADMIN":
```

The system should check:

```python
if user.has_permission("tickets.assign"):
```

Benefits

- Enterprise ready
- Flexible
- Custom roles
- Easier maintenance
- No hardcoded role logic

---

# 4. Business Rules

### Rule 1

Permission names must be globally unique.

---

### Rule 2

Permissions cannot be deleted if assigned to a role.

---

### Rule 3

System permissions cannot be modified by Company Admins.

---

### Rule 4

Permissions should be grouped by module.

---

### Rule 5

Permission names are immutable after release.

---

### Rule 6

New features must define permissions before implementation.

# 13. SQLAlchemy Model Example

```python
class Permission(Base):
    __tablename__ = "permissions"

    permission_id = mapped_column(
        Integer,
        primary_key=True
    )

    permission_name = mapped_column(
        String(150),
        unique=True,
        nullable=False
    )

    module = mapped_column(
        String(100),
        nullable=False
    )

    action = mapped_column(
        String(100),
        nullable=False
    )

    roles = relationship(
        "RolePermission",
        back_populates="permission"
    )
```

# 18. Authorization Flow

```
Incoming Request

↓

JWT Authentication

↓

Load User

↓

Load Role

↓

Load Permissions

↓

Permission Check

↓

Authorized?

│

├── Yes → Continue

└── No → HTTP 403
```

---

# 19. Security Considerations

- Never trust permissions supplied by clients.
- Resolve permissions server-side.
- Cache permissions securely.
- Log permission-denied events.
- Restrict permission management APIs.

---

# 20. Performance Considerations

- Cache permissions in Redis.
- Cache role-permission mappings.
- Load permissions once per request.
- Avoid repeated database queries for authorization.
