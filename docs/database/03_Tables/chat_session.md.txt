# 1. Purpose

The **chat_sessions** table represents an individual conversation between a customer and the AI Customer Support Agent.

A chat session begins when a customer starts a new conversation and ends when:

- Customer closes the chat
- AI closes the conversation
- Chat expires because of inactivity
- Conversation is escalated into a support ticket
- Administrator manually closes the session

A session groups all messages that belong to the same conversation.

The chat_sessions table is responsible for:

---

# 3. Business Rules

### Rule 1

Every session belongs to exactly one company.

---

### Rule 2

Every session belongs to one customer.

---

### Rule 3

A customer may have multiple sessions.

---

### Rule 4

A session contains one or more chat messages.

---

### Rule 5

A session may create zero or one support ticket.

---

### Rule 6

Archived sessions cannot receive new messages.

---

### Rule 7

Soft deletion is not permitted.

Sessions are archived instead.

---

### Rule 8

Every AI response must belong to an existing session.

---

### Rule 9

Session titles are generated automatically from the first conversation unless manually renamed.

---

### Rule 10

Every session must remain tenant isolated.

# 15. SQLAlchemy Model Example

```python
class ChatSession(Base):
    __tablename__ = "chat_sessions"

    session_id = mapped_column(
        BigInteger,
        primary_key=True
    )

    company_id = mapped_column(
        ForeignKey("companies.company_id"),
        nullable=False
    )

    customer_id = mapped_column(
        ForeignKey("users.user_id"),
        nullable=False
    )

    session_uuid = mapped_column(
        String(36),
        unique=True
    )

    messages = relationship(
        "ChatMessage",
        back_populates="session",
        cascade="all, delete-orphan"
    )

    ticket = relationship(
        "Ticket"
    )
```

# 21. Security Considerations

- Every query must include `company_id`.
- Customers can access only their own sessions.
- Company administrators can view company conversations.
- Session UUIDs should be unguessable.
- Conversation metadata must never expose sensitive system information.
- Record session state changes in audit logs.

---

# 22. Performance Considerations

- Cache active sessions.
- Update token statistics asynchronously where possible.
- Archive inactive sessions automatically.
- Paginate chat history.
- Avoid loading messages until requested.
- Use lazy loading for related entities.

When generating code for `chat_sessions`:

2. Archive completed conversations.
3. Always maintain tenant isolation.
4. Update token usage after every AI response.
5. Calculate AI cost using configured pricing.
6. Generate session titles automatically.
7. Support escalation to tickets.
