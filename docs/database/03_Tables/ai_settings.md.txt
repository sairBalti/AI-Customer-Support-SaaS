# 1. Purpose

The **ai_settings** table stores all configurable AI behavior for each company (tenant).

Instead of hardcoding AI parameters inside the application, every AI request reads its configuration from this table.

This enables every company to have different AI behavior without changing application code.

Examples include:

- AI Provider
- LLM Model
- Embedding Model
- Prompt Templates
- Temperature
- Max Tokens
- Confidence Threshold
- Chunk Size
- Vector Database
- Human Escalation Rules

---

### Rule 4

Changes must be recorded in Audit Logs.

---

### Rule 5

Prompt templates are version controlled.

---

### Rule 6

Temperature must remain within supported model limits.

---

### Rule 7

Embedding model and vector dimension must be compatible.

### Rule 8

Inactive configurations cannot be used.

# 15. SQLAlchemy Model Example

```python
class AISetting(Base):

    __tablename__ = "ai_settings"

    ai_setting_id = mapped_column(
        BigInteger,
        primary_key=True
    )

    company_id = mapped_column(
        ForeignKey("companies.company_id"),
        nullable=False,
        unique=True
    )

    created_by = mapped_column(
        ForeignKey("users.user_id"),
        nullable=False
    )

    configuration_uuid = mapped_column(
        String(36),
        unique=True
    )
```

# 21. Security Considerations

- Only administrators can modify settings.
- Audit every configuration change.
- Validate provider compatibility.
- Never expose internal prompts to customers.
- Encrypt provider credentials stored outside this table.
- Restrict configuration APIs.

---

# 22. Performance Considerations

- Cache active configuration.
- Reload cache on updates.
- Avoid reading settings from the database on every token.
- Version prompt templates.
- Validate configuration only during updates.

# 24. Cursor AI Instructions

When generating code for `ai_settings`:

1. Load configuration before every AI request.
2. Cache active settings.
3. Validate provider/model compatibility.
4. Keep prompt templates versioned.
5. Record all configuration changes.
6. Never hardcode AI parameters.
7. Support multiple providers through adapters.
8. Keep ORM models, migrations, repositories, services, and documentation synchronized.

# 27. Architecture Notes

Recommended runtime architecture

```
API Request

↓

Authentication

↓

Load Cached AI Settings

↓

Retriever

↓

Vector Database

↓

Prompt Builder

↓

LLM Adapter

↓

AI Response

↓

Chat History

↓

Analytics
```

The **ai_settings** table acts as the central configuration hub for all AI functionality in the platform. It should be provider-agnostic, version-controlled, cache-friendly, and flexible enough to support future AI models, vector databases, retrieval strategies, and prompt engineering techniques without requiring application code changes.
