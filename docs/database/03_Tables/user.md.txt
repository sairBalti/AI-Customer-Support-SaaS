# 1. Purpose

The **users** table stores all authenticated users within the platform.

Every user belongs to exactly one company (tenant) and is assigned one role.

Users can be:

- Super Administrators
- Company Administrators
- Support Agents
- Customers

The users table is responsible for authentication, authorization, ownership, auditing, and all user-related operations.

---

# 2. Business Responsibilities

The users table manages:

- User authentication
- User profile
- Password management
- Role assignment
- Company membership
- Email verification
- Account status
- Login tracking
- User preferences
- Audit ownership

---

# 3. Business Rules

### Rule 1

Every user belongs to exactly one company.

Exception:

System Super Administrators may belong to the platform company.

---

### Rule 2

Each email address must be unique across the platform.

---

### Rule 3

A user has exactly one role.

---

### Rule 4

Passwords are never stored in plain text.

Only Argon2id (preferred) or bcrypt hashes are stored.

---

### Rule 5

A deleted user is soft deleted.

Historical records remain.

---

### Rule 6

Users cannot access another company's data.

---

### Rule 7

A suspended user cannot log in.

---

### Rule 8

Email verification is required before accessing protected resources (configurable).

---

### Rule 9

Company Administrators cannot promote themselves to Super Administrator.

---

### Rule 10

Users may be logged in from multiple devices simultaneously.

# 11. Validation Rules

## First Name

- Required
- 2–100 characters

---

## Last Name

- Required
- 2–100 characters

---

## Email

- Required
- RFC-compliant email format
- Unique
- Lowercase before storage

---

## Password

Must satisfy password policy:

- Minimum 12 characters
- At least one uppercase letter
- At least one lowercase letter
- At least one number
- At least one special character

Passwords are hashed before persistence.

---

## Phone

Optional.

Store in E.164 format where possible.

---

## Avatar URL

Optional.

Must be a valid HTTPS URL or approved object storage path.

# 13. Authentication Rules

Authentication uses:

- JWT Access Token
- Refresh Token

Access tokens are short-lived.

Refresh tokens are rotated.

Password hashes are never returned by APIs.

---

# 14. Authorization

Authorization is handled using Role-Based Access Control (RBAC).

Supported roles:

- Super Admin
- Company Admin
- Support Agent
- Customer

Permission checks occur before every protected operation.

# 16. SQLAlchemy Model Example

```python
class User(Base):
    __tablename__ = "users"

    user_id = mapped_column(BigInteger, primary_key=True)

    company_id = mapped_column(
        ForeignKey("companies.company_id"),
        nullable=False
    )

    role_id = mapped_column(
        ForeignKey("roles.role_id"),
        nullable=False
    )

    email = mapped_column(
        String(255),
        unique=True,
        nullable=False
    )

    password_hash = mapped_column(String(255))

    company = relationship(
        "Company",
        back_populates="users"
    )

    role = relationship(
        "Role",
        back_populates="users"
    )
```

# 21. Security Considerations

- Never return `password_hash` in API responses.
- Never log passwords.
- Rotate refresh tokens after use.
- Track failed login attempts.
- Lock accounts after configurable failed attempts.
- Record login activity in `audit_logs`.
- Enforce tenant isolation on every query.

---

# 22. Performance Considerations

- Cache authenticated user profiles.
- Index email lookups.
- Paginate user lists.
- Use lazy loading for optional relationships.
- Avoid unnecessary joins when only identity information is required.
