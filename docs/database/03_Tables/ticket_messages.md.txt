# 1. Purpose

The **ticket_messages** table stores every communication exchanged within a support ticket.

Unlike **chat_messages**, which represent AI conversations, **ticket_messages** are designed for human support interactions.

Messages may be created by:

- Customer
- Support Agent
- Company Administrator
- System

Every message belongs to exactly one ticket.

This table provides the complete communication history required for:

- Customer support
- Internal collaboration
- Compliance
- Auditing
- Ticket resolution
- Reporting

---

# 3. Business Rules

### Rule 1

Every message belongs to exactly one ticket.

---

### Rule 2

Messages cannot exist without a parent ticket.

---

### Rule 3

Closed tickets cannot receive customer or public agent replies.

Only internal administrative notes may be added if permitted by business rules.

---

### Rule 4

Messages are immutable.

Edits create a new version in future releases.

---

### Rule 5

Messages must remain in chronological order.

---

### Rule 6

Internal notes are never visible to customers.

---

### Rule 7

Every message belongs to one company.

---

### Rule 8

Soft deletion is not allowed.

Messages are retained for compliance.

# 15. SQLAlchemy Model Example

```python
class TicketMessage(Base):

    __tablename__ = "ticket_messages"

    ticket_message_id = mapped_column(
        BigInteger,
        primary_key=True
    )

    ticket_id = mapped_column(
        ForeignKey("tickets.ticket_id"),
        nullable=False
    )

    company_id = mapped_column(
        ForeignKey("companies.company_id"),
        nullable=False
    )

    sender_id = mapped_column(
        ForeignKey("users.user_id")
    )

    ticket = relationship(
        "Ticket",
        back_populates="messages"
    )
```

# 21. Security Considerations

- Enforce tenant isolation using `company_id`.
- Customers may view only messages from their own tickets.
- Internal notes must never be exposed to customers.
- Validate sender permissions before creating messages.
- Sanitize HTML and Markdown.
- Record all message events in audit logs.

---

# 22. Performance Considerations

- Paginate long conversations.
- Index ticket timelines.
- Cache unread counts.
- Queue notifications asynchronously.
- Lazy-load attachments.
- Archive historical conversations if required.
