# 1. Purpose

The **usage_metrics** table stores aggregated platform usage statistics for each company.

Unlike **audit_logs**, which records every business event, this table stores summarized usage data that powers:

- Subscription limits
- Billing calculations
- AI token consumption
- Analytics dashboards
- Monthly reports
- Usage alerts
- Capacity planning
- Customer success insights

This table is optimized for reporting and should not store raw transactional events.

---

# 2. Business Responsibilities

The usage_metrics table is responsible for

- AI token tracking
- Chat usage
- API usage
- Storage usage
- User activity metrics
- Billing metrics
- Feature usage analytics
- Subscription quota tracking

---

# 3. Business Rules

### Rule 1

Every usage record belongs to one company.

---

### Rule 2

Usage is aggregated by reporting period.

---

### Rule 3

Historical metrics are immutable.

---

### Rule 4

Metrics are updated asynchronously.

---

### Rule 5

Usage metrics must never block application requests.

---

### Rule 6

Usage counters can only increase during an active reporting period.

---

### Rule 7

Subscription quota validation reads from current usage metrics.

---

### Rule 8

Metrics are retained for long-term reporting.

# 14. SQLAlchemy Model Example

```python

    __tablename__ = "usage_metrics"

    usage_metric_id = mapped_column(
        BigInteger,
        primary_key=True
    )

    company_id = mapped_column(
        ForeignKey("companies.company_id"),
        nullable=False
    )

    usage_uuid = mapped_column(
        String(36),
        unique=True
    )
```

# 21. Security Considerations

- Enforce tenant isolation.
- Do not expose other companies' analytics.
- Restrict billing metrics to authorized users.
- Validate reporting permissions.
- Audit metric corrections.
- Protect exported reports.

---

# 22. Performance Considerations

- Update metrics asynchronously.
- Cache dashboard queries.
- Partition historical data.
- Archive old reporting periods.
- Batch aggregation jobs.
- Avoid updating counters synchronously on every request.

# 24. Cursor AI Instructions

When generating code for `usage_metrics`:

1. Never calculate analytics synchronously inside API requests.
2. Update counters through background workers.
3. Store aggregated—not raw—usage.
4. Cache dashboard responses.
5. Support multiple reporting periods.
6. Integrate with subscription limits.
7. Calculate AI costs independently of providers.
8. Keep ORM models, migrations, repositories, services, and documentation synchronized.

# 26. Architecture Notes

Recommended analytics architecture

```
Application Events

↓

Message Queue

↓

Analytics Worker

↓

Usage Aggregator

↓

usage_metrics

↓

Dashboard API

↓

Reports

↓

Billing Engine
```

The **usage_metrics** table is the primary source for operational analytics, subscription enforcement, and billing insights. It should remain highly optimized for read-heavy workloads, support long-term reporting, and integrate seamlessly with background processing, AI cost tracking, and business intelligence systems.
