# 1. Purpose

This document defines the logical and physical relationships between all database entities used in the AI Customer Support Platform.

The ERD serves as the single source of truth for:

- Database Developers
- Backend Developers
- QA Engineers
- DevOps Engineers
- Cursor AI

This document must be reviewed before implementing any table or relationship.

# 8. Relationship Rules

## Company Deletion

A company cannot be deleted if:

- Users exist
- Documents exist
- Tickets exist
- Chats exist

Instead

```
status = INACTIVE
```

---

## User Deletion

Users are soft deleted.

Historical chats remain.

Historical tickets remain.

Audit logs remain.

---

## Document Deletion

Deleting a document removes:

- Chunks
- Embeddings

Chat history remains.

---

## Chat Session

Deleting chat sessions is prohibited.

Only archive them.

---

## Ticket

Tickets are never physically deleted.

Closed tickets remain available for reporting.

# 9. Cascade Strategy

| Relationship | Delete Rule |
|---------------|------------|
| Company → Users | RESTRICT |
| Company → Documents | RESTRICT |
| Company → Tickets | RESTRICT |
| Company → Chat Sessions | RESTRICT |
| Document → Chunks | CASCADE |
| Chat Session → Messages | CASCADE |
| Ticket → Ticket Messages | CASCADE |
| User → Refresh Tokens | CASCADE |

# 14. ERD Validation Checklist

Before implementing or modifying a table, verify:

- Primary key defined.
- Foreign keys defined.
- Tenant ownership identified.
- Required indexes added.
- Cascade rule documented.
- Soft delete policy considered.
- Audit requirements reviewed.
- ORM relationship mapped.
- API impact assessed.
- Documentation updated.

---

# 15. Cursor AI Instructions

When generating models or migrations, Cursor should:

1. Read this ERD before creating new relationships.
2. Respect all cardinalities.
3. Define foreign keys explicitly.
4. Add indexes for foreign keys.
5. Use `company_id` on all tenant-owned entities.
6. Follow cascade and restrict policies.
7. Keep SQLAlchemy relationships synchronized with the ERD.
8. Update this document if relationships change.

---

# Conclusion

This ERD defines the structural foundation of the platform. All database tables, ORM models, repositories, and migrations must remain consistent with the relationships and rules documented here. Any structural change requires updates to this ERD and the corresponding Architecture Decision Record (ADR).
